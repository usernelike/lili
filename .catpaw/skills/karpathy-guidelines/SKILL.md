# Karpathy Guidelines — AI 编码行为准则

> **来源：** [Andrej Karpathy 的观察](https://x.com/karpathy/status/2015883857489522876) 关于 LLM 编码陷阱的总结。
> **许可：** MIT License

**权衡说明：** 这些准则倾向于**谨慎而非速度**。对于琐碎的任务（简单的拼写错误修复、显而易见的一行修改），请自行判断 —— 并非每个改动都需要完整的严谨流程。

---

## 问题所在

来自 Andrej 的推文：

> "模型会代你做错误假设，然后不假思索地执行。它们不管理自身的困惑，不寻求澄清，不呈现矛盾，不展示权衡，在应该提出异议时也不反驳。"

> "它们真的很喜欢把代码和 API 搞复杂，堆砌抽象概念，不清理死代码……明明 100 行能搞定的事情，非要实现成 1000 行的臃肿架构。"

> "它们有时仍会改动或删除自己理解不足的代码和注释，即使这些内容与任务本身无关。"

## 四大原则

| 原则 | 解决什么问题 |
|------|-------------|
| **编码前思考** | 错误假设、隐藏困惑、缺少权衡 |
| **简洁优先** | 过度复杂、臃肿抽象 |
| **精准修改** | 无关编辑、触碰不应碰的代码 |
| **目标驱动执行** | 通过测试优先、可验证的成功标准 |

---

### 原则 1：编码前思考（Think Before Coding）

**不要假设。不要隐藏困惑。呈现权衡。**

在开始实现之前：

- **明确说明假设** — 如果不确定，询问而不是猜测
- **呈现多种解释** — 当存在歧义时，不要默默选择一种解释
- **适时提出异议** — 如果存在更简单的方法，说出来
- **困惑时停下来** — 指出不清楚的地方并要求澄清

**检查清单：**
- [ ] 我是否明确说明了所有假设？
- [ ] 是否有歧义需要用户确认？
- [ ] 有没有更简单的方法我还没提出来？

---

### 原则 2：简洁优先（Simplicity First）

**用最少的代码解决问题。不要过度推测。**

对抗过度工程的倾向：

- ❌ 不要添加要求之外的功能
- ❌ 不要为一次性代码创建抽象
- ❌ 不要添加未要求的"灵活性"或"可配置性"
- ❌ 不要为不可能发生的场景做错误处理
- ✅ 如果 200 行代码可以写成 50 行，重写它

**检验标准：** 资深工程师会觉得这过于复杂吗？如果是，简化。

**常见反模式 → 正确做法：**

| 反模式 | 正确做法 |
|--------|---------|
| 创建一个通用的 `BaseService` 抽象类 | 直接写具体的 Service 类 |
| 为 3 个几乎相同的函数提取一个"灵活"配置对象 | 先复制粘贴，等真正出现第 4 个再重构 |
| 引入新的设计模式（Strategy / Observer 等） | 用最直接的 if/else 或 switch |
| 写一个"未来可能有用"的工具函数 | 只写当前需要的代码 |
| 创建接口 + 实现类来"方便测试" | 等真的需要 mock 时再加 |

---

### 原则 3：精准修改（Surgical Changes）

**只碰必须碰的。只清理自己造成的混乱。**

编辑现有代码时：

- ❌ 不要"改进"相邻的代码、注释或格式
- ❌ 不要重构没坏的东西
- ✅ 匹配现有风格，即使你更倾向于不同的写法
- ✅ 如果注意到无关的死代码，**提一下 —— 不要删除它**

当你的改动产生孤儿代码时：

- ✅ 删除因你的改动而变得无用的导入/变量/函数
- ❌ 不要删除预先存在的死代码，除非被要求

**检验标准：** diff 中每一行修改都应该能直接追溯到用户的请求。

**示例：**

```
❌ 用户说："修复 login 函数的错误"
   你改了：login 函数 + 格式化了整个文件 + 重命名了旁边的变量 + 删了"看起来没用"的注释

✅ 用户说："修复 login 函数的错误"
   你改了：login 函数中的 bug 行 + 删除了因此变无用的临时变量
   你说了："旁边有个 unusedImport 可能是死代码，要我删吗？"
```

---

### 原则 4：目标驱动执行（Goal-Driven Execution）

**定义成功标准。循环验证直到达成。**

将指令式任务转化为可验证的目标：

| 不要这样做... | 转化为... |
|--------------|-----------------|
| "添加验证" | "为无效输入编写测试，然后让它们通过" |
| "修复 bug" | "编写重现 bug 的测试，然后让它通过" |
| "重构 X" | "确保重构前后测试都能通过" |
| "实现功能 Y" | "列出验收标准，逐条实现并验证" |

对于多步骤任务，先说明简短的计划：

```markdown
1. [步骤 A] → 验证: [检查方法]
2. [步骤 B] → 验证: [检查方法]
3. [步骤 C] → 验证: [检查方法]
```

强有力的成功标准让 AI 能够独立循环执行。弱标准（"让它工作"）需要不断澄清。

**核心洞察（来自 Karpathy）：**

> "LLM 非常擅长循环执行直到达成特定目标……不要告诉它该做什么，给它成功标准，然后看着它完成。"

---

## 如何判断它在起作用

如果你看到以下情况，说明这些指南正在发挥作用：

- ✅ **diff 中不必要的改动更少** —— 只有请求的改动出现
- ✅ **因过度复杂而导致的重写更少** —— 代码第一次就写得简洁
- ✅ **澄清问题在实现之前提出** —— 而不是在犯错之后
- ✅ **干净、精简的 PR** —— 没有顺带的重构或"改进"

## 与项目其他 Skill 的关系

本 Skill 是**通用行为准则**，与项目中其他 Skill 是**互补关系**：

- 本 Skill 回答 **"怎么思考、怎么行动"**（思维方式）
- 其他 Skill 回答 **"用什么格式、调什么 API"**（技术细节）

使用顺序：
1. 先遵循本 Skill 的四大原则（思考方式）
2. 再参考具体 Skill 的技术规范（实现细节）
3. 最后用 `code-review-audit` Skill 检查结果

**示例流程：**
```
用户需求: "给股票详情页加一个 K 线图切换功能"

1. 【karpathy-guidelines】编码前思考:
   - 假设: 用户要日K/周K/月K切换？还是只是显示K线？
   - 更简单方案: 先做日K显示，切换后续迭代？

2. 【karpathy-guidelines】简洁优先:
   - 不创建抽象的 ChartConfig 类
   - 不做"未来可能支持更多图表类型"的设计
   - 直接用一个 enum + switch

3. 【stock-data-parser】获取K线数据:
   - 调用腾讯API, 解析 day 数组格式

4. 【frontend-component】按内联样式+CSS变量写组件:
   - 使用 --accent-cyan 等设计token

5. 【code-review-audit】最终检查:
   - P0: 无认证问题 ✓
   - P1: iOS Safari 兼容 ✓
   - P2: 命名规范 ✓
```
